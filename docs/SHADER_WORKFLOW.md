# Workflow шейдеров Xbox 360

Файл: `.github/workflows/shaders.yml`.
Название в Actions: **Experimental Xbox 360 shaders**.

## Запуск

1. Сначала влейте ветку с workflow в основную ветку через PR. GitHub требует
   `workflow_dispatch` в default branch для появления ручного запуска.
2. В **Actions → Experimental Xbox 360 shaders → Run workflow** вставьте
   прямую HTTPS-ссылку на ZIP в поле **`zip_url`**. Ссылка на страницу
   предпросмотра вместо скачивания не подходит.
   **Это поле не секретное**: не используйте его для ссылок, которые нельзя
   раскрывать читателям репозитория. Для приватной подписанной ссылки оставьте
   `zip_url` пустым и задайте Actions secret `SHADERS_ZIP_URL` (самостоятельно
   или через помощник `scripts/prepare_shader_link.py`). При заполненном
   `zip_url` используется именно оно, иначе — секрет.
3. Поле **`sha256` оставьте пустым** для автоматического вычисления суммы.
   Не вставляйте туда ссылку. Если хотите проверить совпадение с локальным
   ZIP, укажите его SHA-256:
   ```powershell
   (Get-FileHash .\shaders.zip -Algorithm SHA256).Hash.ToLower()
   ```
   Автоматический расчёт суммы не подтверждает подлинность источника.
4. Для скачивания результата включите `upload_result`. **Артефакт доступен
   читателям репозитория, а не только вам!** Он содержит производные игровые
   ресурсы. Рекомендуется приватный репозиторий; не публикуйте их без разрешения.
   По умолчанию загрузка выключена: workflow лишь проверяет конвертацию.
5. После успешного запуска скачайте artifact `experimental-shaders-<run-id>`.
   Срок хранения — один день. ZIP и извлечённые бинарники туда не включаются.

## Что делает workflow

- Собирает закреплённый submodule XenosRecomp и его DXC на Windows/ClangCL.
  Debug сохраняет assertions upstream для обнаружения ошибок конвертации.
  Собирается только цель `XenosRecomp`; Zstd используется статически.
  Ненужные DLL Zstd и CLI-утилиты отключены, чтобы не запускать Windows RC
  на несовместимых заголовках Clang (`RC1012`).
- Скачивает ZIP по `zip_url` или из секрета; проверяет лимит 256 MiB и, если задан, ожидаемый SHA-256.
- Проверяет пути ZIP, дубликаты, последовательность частей `.ar.NN`.
- Объединяет части и ищет несжатые контейнеры Xenos. `.arl` — индексы, они
  не участвуют в поиске. Это не универсальный AR-распаковщик.
- Дедуплицирует контейнеры, генерирует HLSL и экспериментальный C++-кэш
  DXIL/SPIR-V, проверяет количество записей и непустые payload.
- Выдаёт `hlsl/`, `shader_cache.experimental.cpp`, `report.json`, `README.txt`.
- Удаляет временные игровые данные даже при ошибке.

## Честные ограничения

Реальный архив пользователя пока не проверен. Если хотя бы один AR не содержит
распознаваемых несжатых шейдеров, задача остановится, а не выдаст пустой кэш.
Сжатые AR (например, LZX) нужно предварительно распаковать совместимым
инструментом Hedgehog Engine. Проверка заголовков не является полной проверкой
безопасности контейнеров: используйте только собственные доверенные дампы.

XenosRecomp рассчитан прежде всего на Unleashed и может потребовать адаптации
под Generations. Используется общий shader_common.h, без UNLEASHED_RECOMP.
Успешный DXC не доказывает полноту поиска или визуальную корректность.

Выходной кэш upstream **не совместим с текущим ShaderCacheEntry проекта**:
он содержит offsets, specialization masks, Zstd-сжатые DXIL и smol-v SPIR-V.
Не копируйте его в runtime и не включайте SONIC_GENERATIONS_HAVE_SHADER_CACHE
до адаптации ABI, декомпрессии, привязок ресурсов и GPU-бэкенда.

## Локально

Соберите XenosRecomp командами из workflow и выполните:

```powershell
python scripts/shader_pipeline.py --zip C:\dumps\shaders.zip --sha256 <SHA256> --xenos build-shaders/XenosRecomp/Debug/XenosRecomp.exe
```

Результат: `private/shader-build/result/` (исключён из Git).
Для повторного запуска используйте новую папку `--work private/run2` или
удалите старую вручную. Уже существующая рабочая папка отвергается, чтобы
старые результаты не попали в новый artifact.

## Ошибка undeclared identifier b128/b129/b130

Upstream может генерировать условные переходы с необъявленными boolean-регистрами.
Pipeline проверяет HLSL до пакетной компиляции DXC и останавливается на первом
таком шейдере. Это диагностика, **не исправление семантики рекомпилятора**:
значения нельзя заменять нулями или произвольно перенумеровывать.

При включённом `upload_result` неудачный запуск публикует отдельный
`shader-diagnostics-<run-id>`: проблемный HLSL и JSON с SHA-256 контейнера и
списком отсутствующих регистров. Исходный бинарник не публикуется. Artifact
также содержит производный игровой ресурс, поэтому действуют те же ограничения
доступа. Для исследования таблицы определений понадобится соответствующий
исходный контейнер или архив из доверенного источника.

## Boolean-регистры вне reflection (b128/b129/b130)

Workflow использует закреплённый форк **Player124413/XenosRecomp** и больше не
применяет старый `patches/xenos-generations-booleans.patch` от upstream.
Форк сам обрабатывает boolean-регистры через packed `g_Booleans`; отдельного
банка `b3, space4` он не добавляет. Его схема и ограничения описаны в
[TOOLCHAIN.md](TOOLCHAIN.md). Совместимость с реальным native state ещё должна
быть реализована и проверена — успешная компиляция не доказывает корректность
условных ветвлений в игре.

Pipeline явно выбирает `--api vulkan`, сохраняет `compiler-report.json` и
диагностику неудачных шейдеров. Неполная конвертация не разрешается через
`--allow-failures`. Проверяется наличие SPIR-V; DXIL для этого режима не нужен.

Время обработки: pipeline сначала сохраняет каждый HLSL отдельным процессом,
затем XenosRecomp повторно переводит код и компилирует SPIR-V. Debug,
тысячи контейнеров и финальное Zstd-сжатие максимального уровня также стоят
времени. Рост процента после ошибок не означает, что повреждённые шейдеры
исправились: работа выполняется параллельно.

## Строгая проверка семантических предупреждений

У закреплённого форка есть fallback для boolean-регистров вне packed-диапазона:
он способен сгенерировать `if (true)` / `if (false)` вместо исходного условия.
Это может пройти DXC и SPIRV-Tools, но не гарантирует поведения Xbox 360.
Pipeline теперь отвергает такие помеченные fallback-ветви ещё на стадии HLSL.
Обычные константные ветвления и корректные packed-регистры без reflection не
отвергаются только за сам факт их наличия.

После компиляции обязателен корректный `compiler-report.json`: Vulkan, точное
число ожидаемых/успешных шейдеров, ноль ошибок и предупреждений. На этом этапе
**любое предупреждение останавливает pipeline**, без автоматического списка
исключений. Отчёт сохраняется в diagnostics, отвергнутый cache удаляется из
каталога успешного результата. Поле `runtime_ready` остаётся false.

Проверка покрыта unit-тестами и тестами pipeline с имитацией компилятора,
включая сохранение диагностики и отсутствие публикации отвергнутого cache.
Она не исправляет шейдеры автоматически и не доказывает отсутствие fallback
в уже опубликованном cache: для него нужен исходный отчёт или повторная сборка.
